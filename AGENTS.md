# Правила работы в FaceFlow

Эти правила относятся к этому репозиторию. Отвечайте кратко по-русски: результат, существенные проверки и ограничения. Непроверенные числа и качество не выдавайте за подтверждённый факт.

## Перед изменением

1. Прочитайте ближайшие инструкции, [README](README.md), соответствующие места [архитектуры](docs/ARCHITECTURE.md) и [API](docs/API.md), затем затронутый код и его вызывающие.
2. Обновите сведения о удалённых ветках через `git fetch`, просмотрите ветки, открытые PR и issues доступным CLI/API. Определите владельца задачи и границы файлов; не дублируйте активную работу. При отсутствии доступа прямо укажите, что не удалось проверить.
3. Проверьте `git status` и существующий diff. Работайте в отдельной ветке. Сохраняйте чужие изменения; перед правкой сохраните preimage. Если файл изменился параллельно, согласуйте обе версии, не затирайте одну из них.

## Изменения и проверки

- Делайте простое полноценное решение в согласованном объёме. Не добавляйте будущие возможности, зависимости или процессы про запас. В разрешённом цикле ниже самостоятельно выбирайте ограниченный пункт [PLAN](PLAN.md) в рамках продукта.
- Основные точки входа: [app.py](app.py) - HTTP, SQLite, файлы и запуск; [recognition.py](recognition.py) - inference; [web/app.js](web/app.js), [web/style.css](web/style.css), [web/index.html](web/index.html) - интерфейс; [tests/test_flow.py](tests/test_flow.py) - проверки; [models/manifest.json](models/manifest.json) - происхождение и SHA-256 моделей.
- Проверяйте соразмерно изменению: `python -m unittest discover -s tests -v`; существенные изменения интерфейса проверяйте в браузере. После изменения API проверяйте клиент и сервер вместе. Успешные проверки повторяйте после новых изменений или конкретного сомнения.
- Не объявляйте синтетические тесты оценкой реального качества. Порог, лицензии и способы скачивания моделей описывайте по текущим файлам. Если измерений нет, пишите об этом прямо.
- Завершайте созданные временные процессы. Пользовательские результаты сохраняйте в `outputs`, промежуточные материалы - в `work` либо принятом каталоге проекта.

## Commit и push

По явной просьбе владельца от 4 октября 2026 для этого проекта действует разрешение на обычный commit и push рабочей ветки после небольшого завершённого проверенного изменения и перед передачей результата. Перед commit просмотрите diff и убедитесь, что включены только изменения своей задачи; перед push проверьте целевую ветку и отсутствие секретов. Это проектное разрешение не распространяется на глобальную конфигурацию, продакшен-выкатки, force push, перезапись чужих изменений или разрушительные действия.

Не коммитьте и не загружайте реальные лица, фотографии пользователей, базы, ключи, секретные URL и локальные каталоги `data/`, `work/`, `.venv/`, скачанные веса моделей. Происхождение синтетических данных описано в [tests/fixtures/PROVENANCE.md](tests/fixtures/PROVENANCE.md). Не отправляйте сообщения людям от имени владельца без отдельной просьбы. Если текущая задача явно запрещает commit/push, соблюдайте этот запрет.

Лицензию проекта самостоятельно не выбирайте. Перед текстом от имени владельца следуйте его доступным локальным инструкциям по стилю; персональные файлы и переписку в репозиторий не переносите.

## Оформление репозитория

Keep the public README concise and in English, with a separate Russian guide. Use the FaceFlow nameplate, CI and Stack badges, and the verified release link. Use current product captures with test data.

Link badges to sources. Use the GitHub Actions badge for CI. Verify a run on the final revision after changing CI. Use the run summary for coverage and the `upload_coverage` input for downloadable HTML and JSON. Recognition accuracy requires separate evidence.

## Передача

Сообщите завершённый результат, выполненные проверки, оставшиеся риски и изменённые пути. Не скрывайте блокер за общим «готово». При длительной передаче оставьте короткий `HANDOFF.md` с целью, решениями, проверенным результатом и следующим шагом; новую пользовательскую задачу создавайте только по прямой просьбе.

## Разрешённый цикл улучшений

Прямое поручение пользователя от 05.10.2026 в чате «Инструменты» `01a10967-c5f8-7373-8069-a3c5b4197693`: после описания автономного цикла с включением проверенного кода в main пользователь ответил «исправь».

Самостоятельно выбирай следующий ограниченный блок улучшений в рамках продукта, реализуй, проверяй и ревьюь diff, делай частые законченные коммиты, включай проверенный результат в main и выполняй обычный push. Проверь итоговый удалённый SHA и CI; затем продолжай следующую итерацию. PR используй только когда он помогает координации или требуется защитой ветки; сам заверши его слияние после необходимых проверок, без ожидания пользователя. Не накапливай зависимые PR вместо включения готового кода в main. Отдельный issue нужен при пересекающейся работе, а не для каждой самостоятельной правки.

Разрешение включает обычное слияние собственных проверенных изменений и push main, сохраняется после handoff и заменяет прежний запрет самостоятельного merge, обязательный PR и повторный выбор каждой задачи пользователем. Сохраняй чужие изменения, несведённые ветки, PRIVATE и опубликованную историю. Защиту веток и необходимые проверки не обходи; при конфликте безопасно согласуй код и повтори затронутые проверки. Расходы, смена цели, force-push, удаление чужой работы, публикация личных материалов и production-выкатка требуют отдельного основания. Если push main автоматически выкатывает production, остановись до этого действия и сообщи конкретный блокер.
